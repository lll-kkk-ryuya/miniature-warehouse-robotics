3. free_fleet と今回PJの関係

そのまま採用しない: free_fleet runtime

free_fleet は EasyFullControl Fleet Adapter と robot ごとの Zenoh bridge を使う。 各ロボット側に非 namespaced Nav2 stack がある分散構成を想定する。

  • free_fleet そのものは No-Go と記録済み。docs/mode-c/11c-traffic-mode-c.md:207-215
  • 今回PJは中央 Jetson 上の /bot1 / /bot2 namespaced Nav2 なので前提が逆。docs/mode-c/11c-traffic-mode-c.md:217-239
  • GitHub README でも robot の navigation stack は non-namespaced、Zenoh bridge 側で robot name namespace を付ける前提。open-rmf/free_fleet README:260-265

採用方針: 自作 EasyFullControl adapter

Open-RMF core の Traffic Schedule / Negotiation はそのまま使う。Nav2 への接続だけ、Zenohを外して自作adapterで直接つなぐ。

  • 第一候補は rmf_fleet_adapter EasyFullControl API で自作し、/bot{n} Nav2 を直接駆動。docs/mode-c/11c-traffic-mode-c.md:245-256
  • Fleet Adapter は navigate / stop / execute_action と RobotState 更新を実装する想定。ws/src/warehouse_rmf_adapter/warehouse_rmf_adapter/fleet_adapter.py:46-62
  • 公式 tutorial でも fleet adapter は robot position 更新、task response、vendor robot control を担う。OSRF Fleet Adapter Tutorial:24-40

7. Open-RMF が確率的ではない理由

誤読: 確率で通す

「衝突しそうだが多分大丈夫」という確率判定を motion に直接使う設計ではない。 速度やモータ指令を RMF から直接出すことも不採用。

docs/productization/07-layer-tool-decision-matrix.md:57 docs/productization/11-l2-contract-governance-traffic-box.md:58-62

正しい理解: 予定軌道と時間の調停

各 fleet adapter が予定 itinerary を Traffic Schedule に出し、schedule が未来の意図の衝突を検出する。 conflict があれば fleet manager どうしが itinerary を提案し、judge が組み合わせを選ぶ。

OSRF RMF Core Overview:33-46 docs/mode-c/11c-traffic-mode-c.md:59-63
